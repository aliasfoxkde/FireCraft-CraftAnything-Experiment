## Documentation and workflow validation

The documentation entry point is [`docs/README.md`](README.md). It groups product/releases,
tutorials, feature guides, reference, troubleshooting/support, development/architecture, and
planning/evidence. A reader moves from the category map to a focused page rather than a long list
of task phrases. The root README stays the concise product/download entry point.

The reusable workflow process is in
[`DOCUMENTATION-AND-WORKFLOW-EVIDENCE.md`](DOCUMENTATION-AND-WORKFLOW-EVIDENCE.md), with a stable
scenario catalog at [`workflows/README.md`](workflows/README.md) and a per-run receipt form at
[`testing/workflow-evidence-template.md`](testing/workflow-evidence-template.md). Each feature flow
records its start state, user actions, expected transitions, undo/recovery route, keyboard path,
surface, artifact identity, environment, assertions, logs/traces, real application screenshots,
reviewer notes, and docs follow-through. Failed runs are preserved as diagnostic evidence; guides
are written from passing runs. A screenshot alone proves appearance, and a headless test proves
only the behavior it exercises.

The workflow map and template are present and linked. Current evidence is not sufficient to call
the documentation or product comprehensively verified: tutorials do not yet cover every shipped
feature with current screenshots, and the catalog leaves native/browser clipboard, pop-out canvas,
tools, complete path editing, file dialogs, raster effects, save recovery, and accessibility flows
partial or unverified. The audit marks these accurately in
[`the workflow catalog`](workflows/README.md) and converts new execution work into
[`the task ledger`](TASKS.md).
